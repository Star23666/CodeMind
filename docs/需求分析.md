# CodeMind 需求分析

## 1. 项目定位

CodeMind 是面向计算机知识学习场景的 RAG 知识库系统。系统支持用户上传课程资料、实验文档和技术文档，经过文本解析、切分、Embedding 向量化和 Chroma 入库后，用户可以进行语义检索、获得带来源依据的回答，并把资料整理为可追溯的知识地图。

系统采用前后端分离结构：前端负责登录、文档管理、问答、历史和知识地图交互；后端负责认证、文档处理、知识库管理、语义检索、RAG 问答、知识地图任务和业务数据管理；MySQL 保存结构化业务数据，Chroma 保存文本片段向量和检索元数据，原始文件保存在上传目录或 Docker 命名卷中。

## 2. 用户角色

| 角色 | 说明 | 主要操作 |
| --- | --- | --- |
| 普通用户 | 使用系统管理学习资料并进行知识问答的学习者 | 注册登录、管理私人知识库、共同使用公共知识库、上传文档、检索与提问、核对来源、查看历史、生成和学习知识地图 |
| 管理员 | 维护公共资料、账号、异常和反馈数据的管理者 | 编辑公共知识库信息、管理全部公共文档、启停账号、查看服务状态和反馈详情；私人资料仅显示脱敏状态 |
| 外部模型服务 | 在线 LLM API 与 Embedding API | 接收后端请求，返回文本向量或回答内容 |

## 3. 功能需求

### 3.1 用户注册登录管理

- 用户可以注册、登录、退出，并通过登录状态访问受保护接口。
- 用户密码必须以哈希形式保存，数据库不保存明文密码。
- 普通用户只能访问本人私人知识库、私人文档、问答历史和反馈数据，同时可以访问全站公共知识库。
- 普通注册接口始终创建普通用户；初始管理员由服务器命令行脚本从已有用户中安全提升。
- 管理员可维护全部公共文档，并查看系统级反馈和异常状态数据。

### 3.2 知识库管理

- 系统提供一个没有固定 ID 的全局公共知识库，所有登录用户看到的是同一条记录。
- 用户可以创建、编辑、删除自己的私人知识库，并向公共知识库上传资料。
- 普通用户不能编辑或删除公共知识库；管理员可以修改其名称和描述，但公共知识库本身不能删除。
- 知识库字段包括名称、描述、可见范围和可空的所属用户；公共库 `owner_id` 为空。
- 同一用户下知识库名称不可重复。
- 知识库用于限定文档归属、检索范围和问答范围。
- 问答、上传和语义检索页面默认选择当前用户的私人知识库；公共库必须由用户明确选择。

### 3.3 文档上传与管理

- 用户可以上传 PDF、DOCX、Markdown、TXT 等计算机学习资料。
- 系统应校验文件类型、文件大小和基础信息。
- 文件保存到本地上传目录后，应在 MySQL `documents` 表中记录文件名、类型、大小、路径、所属知识库、所属用户和处理状态。
- 文档处理状态统一为 `pending`、`processing`、`completed`、`failed`、`cancelled`。
- 用户可以查看本人私人文档和全部公共文档的列表、详情、原文、上传者、处理状态和切片数量。
- 公共文档只能由上传者或管理员取消、重建和删除；私人文档仍只允许本人管理。
- 同一文档不得被重复领取或并发重建；用户可以取消等待中或处理中的任务。
- 服务重启后应自动恢复中断任务；重建失败或取消时应保留上一次可用索引。
- 选择公共知识库时必须持续提示公开范围；提交上传前再次展示文件名、目标库名称和全站可见风险。
- 已完成的私人文档可以在当前用户的私人知识库之间移动；禁止跨用户移动以及私人/公共范围互转。
- 移动操作必须同步更新 `documents`、`document_chunks`、文档级知识地图归属和 Chroma metadata；任一阶段失败时回滚并补偿，历史问答来源快照保持原样。

### 3.4 文档解析、切分与入库

- 系统读取待处理文档，提取文本内容。
- 文本按合理粒度切分为片段，并保留文档编号、知识库编号、片段序号、页码或偏移位置等元数据。
- 系统调用 Embedding API 生成片段向量。
- 向量、片段文本和 metadata 写入 Chroma；片段结构化信息写入 MySQL `document_chunks` 表。
- Chroma 中的向量编号必须与 MySQL `document_chunks.vector_id` 一一对应。

### 3.5 语义检索与文档直接查看

- 用户可以输入自然语言问题或检索词，在指定知识库中召回相关片段。
- 私人库同时按 `knowledge_base_id + owner_id` 隔离；公共库按 `knowledge_base_id` 召回所有上传者的资料。
- 检索时应先将问题向量化，再从 Chroma 中按相似度召回候选片段。
- 默认召回 `top_k=4` 个片段，相似度阈值默认 `0.45`，余弦相似度取值范围为 `[-1, 1]`。该值针对当前 `Qwen/Qwen3-VL-Embedding-8B`、4096 维向量的测试资料调整，更换模型、维度或切分策略后必须重新评估。
- 检索结果需包含文档编号、片段编号、文档名、片段序号、页码、相似度、片段文本和跳转地址。
- 用户可以从检索结果打开文档片段，用于直接查看原文依据。
- 前端提供独立检索入口，并展示加载、无结果、错误和无权限状态；结果卡展示文件名、片段序号、页码、分数和来源跳转。

### 3.6 RAG 问答

- 用户在指定知识库内提交问题。
- 系统可根据上下文对原问题进行重写，生成更适合检索的问题。
- 系统对检索问题进行 Embedding，召回 `top_k=4` 个候选片段，并按相似度阈值过滤低相关片段。
- 通过 rerank 将更相关的片段排在前面，默认保留 `rerank_top_n=2` 个片段进入 prompt。
- 系统将用户问题、重写问题和引用片段组装为 prompt，调用在线 LLM API 生成回答。
- 回答应尽量基于检索片段生成；当检索结果不足时，应明确说明资料依据不足。
- 问答结果保存到 MySQL `qa_records` 表，来源引用保存到 `qa_sources` 表。

### 3.7 来源引用与引用跳转

- 每条回答应返回来源引用列表。
- 来源引用包含文档编号、片段编号、文档名、片段序号、页码或位置、相似度、片段快照和跳转地址。
- 用户点击来源引用后，应能定位到对应文章或文档片段，以便核对回答依据。
- 来源快照应保存到 `qa_sources.source_text`，避免后续文档变化影响历史回答追溯。

### 3.8 问答历史

- 系统保存用户问题、重写问题、回答、来源数量、创建时间和来源引用。
- 用户可以按知识库查看历史问答列表。
- 用户可以进入某条问答记录查看完整回答和引用来源。
- 删除原文后，历史记录仍需保留文件名、片段序号、页码和文本快照；失效的原文跳转应置空。

### 3.9 知识地图

- 用户可以选择整个知识库或单个已完成解析的文档生成知识地图。
- 生成过程以后台任务执行，并返回排队、读取资料、整理上下文、分批提炼、合并结构、校验来源和组装画布等进度。
- 系统应限制同一后端实例对 LLM 的并发调用；某批调用失败时取消其余调用，避免继续消耗 API。
- 地图节点分为 `overview`、`chapter`、`concept` 和 `detail`，可包含摘要、1 至 3 条关键记忆点、学习建议、来源和子节点。
- 私人地图节点引用的片段必须属于当前用户和知识库；公共地图可引用同一公共库中任意上传者的片段。模型返回的未知片段编号必须丢弃。
- 用户可以针对节点来源提问，也可以让 AI 根据节点来源扩展子节点。
- 用户可以创建、打开、更新和删除地图历史版本，系统保存地图 JSON 和画布状态。
- 前端应支持节点搜索、路径导航、相关资料检索、画布缩放与布局、分支折叠、全屏和多格式导出。
- 前端可在浏览器本机记录节点掌握状态，并显示掌握进度和继续学习入口；该状态不作为跨设备同步数据。

### 3.10 用户反馈与测试评估

- 用户可以对某条回答提交 1 到 5 分评分和文字反馈。
- 同一用户对同一条回答只能提交一次反馈。
- 管理员或测试人员可查看反馈数据，用于评估回答准确性、来源匹配度和检索质量。
- 后端必须校验问答归属，将反馈持久化到 `feedbacks`，重复提交返回冲突；管理员可以按评分、用户和知识库筛选。
- 用户可在回答结果和历史详情中查看本人反馈；提交后评分与文字反馈只读，不允许重复修改。
- 管理员反馈列表展示用户主动提交的评分和文字评价并支持筛选；公共库反馈可展示问题、回答和来源数量，私人库反馈必须隐藏知识库名称、问题、回答和来源正文。

### 3.11 用户个人大模型配置

- 用户可以保存、测试、启用、停用和删除个人 OpenAI 兼容 LLM 配置。
- API Key 由后端加密存储，前端和查询接口只能看到末四位掩码。
- 个人配置启用后，RAG 问答、知识地图和 AI 出题使用该配置；调用失败时返回明确错误，不自动消耗系统模型额度。
- 未启用个人配置，或删除个人配置后，继续使用服务器环境变量中的系统模型。
- 连接测试需要区分认证失败、超时、模型不存在和 API 接口地址错误。
- 用户不能读取或启用其他用户的配置；自定义地址必须通过 HTTPS、域名白名单和 SSRF 校验。
- Embedding 继续使用服务器统一配置。AI 出题复用同一用户模型解析服务和同一次运行时解析结果。

### 3.12 多知识库 AI 定制练习

- 用户可以同时选择 1 至 5 个有权读取的私人或公共知识库，设置 5 至 20 题、难度、主题和题型。
- 支持单选、多选、判断、填空、简答和情景应用题，可指定题型或随机混合。
- 后端在知识库内部按文档轮询、再在多个知识库之间轮询抽取已完成片段，并限制片段数、字符数和保守 Token 预算，不能让单个长文档占满上下文。
- 出题使用后台临时会话展示进度；任务执行前再次校验知识库权限，防止排队期间权限变化造成越权。
- 模型必须返回结构化 JSON；题目数量、选项、答案、题型、认知层级、来源编号和整套题的文档覆盖度经 Pydantic 完整校验，有限重试仍无效时不保存损坏题目。
- 进阶练习至少 40% 为应用或分析题；挑战练习至少 70% 为应用或分析题，且至少 40% 为分析题。
- 获取题目接口只返回题干、选项和来源数量。答案、解析与来源正文只在提交后返回。
- 单选、多选、判断题自动评分；填空题支持标准答案或全部关键词匹配；简答和情景题返回参考答案供用户自评。
- 每道题至少引用一个真实片段，结果页可以筛选折叠、完成主观题自评并在新标签页核对原文；已提交结果可在当前标签页刷新后恢复，但不形成服务端历史。
- 出题会话只能由创建者访问。提交或主动放弃时立即删除，过期时由后台任务清理，不形成长期练习历史。
- 启用个人模型时，生成和结构重试都使用同一个人配置，调用失败不回退；未启用个人模型时使用系统模型。

### 3.13 管理员中心

- 仅管理员可以访问管理接口和前端管理中心，普通用户访问后端返回 `403`，访问前端路由进入无权页面。
- 管理员可查看 MySQL、Chroma 就绪状态、用户/文档/反馈统计和最近失败任务的错误摘要。
- 管理员可按用户名、邮箱、角色和状态筛选用户，并启用或停用账号；不能停用自己，也不能停用最后一个有效管理员。
- 停用账号时递增 `token_version`，使该账号已签发的 JWT 立即失效。
- 管理员可以筛选全部文档和任务，但私人文档仅展示编号、所有者和状态；具体错误、文件名、知识库名称、原文或片段均不展示，也不能执行管理操作。
- 公共文档可以由管理员重建和删除；管理员可以筛选并查看问答反馈详情。

## 4. 数据需求

### 4.1 MySQL 业务数据

MySQL 保存结构化业务数据，建表脚本位于 `database/schema.sql`，表名与用途如下：

| 表名 | 用途 |
| --- | --- |
| `users` | 用户账号、邮箱、角色、状态和密码哈希 |
| `knowledge_bases` | 知识库名称、描述、可见范围、可空用户归属和全局公共唯一约束 |
| `documents` | 上传文档的文件信息、所属知识库、所属用户和处理状态 |
| `document_chunks` | 文档片段文本、片段位置、页码和 Chroma 向量编号 |
| `qa_records` | 用户问题、重写问题、回答和来源数量 |
| `qa_sources` | 回答引用的来源片段快照、排序和相似度 |
| `feedbacks` | 用户对回答的评分和文字反馈 |
| `mind_map_histories` | 知识地图结果 JSON、标题、节点数和画布状态 |
| `mind_map_jobs` | 地图后台任务、阶段、进度、结果和失败原因 |
| `quiz_sessions` | AI 出题临时会话、知识库范围、配置、进度和过期时间 |
| `quiz_questions` | 临时题目、答案、解析和来源快照，随会话级联删除 |

### 4.2 Chroma metadata

Chroma 每条向量记录应至少保存以下 metadata：

| 字段 | 说明 |
| --- | --- |
| `owner_id` | 文档所属用户编号 |
| `knowledge_base_id` | 所属知识库编号 |
| `document_id` | 来源文档编号 |
| `chunk_id` | MySQL 文档片段编号 |
| `chunk_index` | 文档内片段序号 |
| `file_name` | 来源文件名 |
| `page_no` | 页码或章节位置 |
| `start_offset` | 片段开始偏移 |
| `end_offset` | 片段结束偏移 |

## 5. 非功能需求

- 可追溯性：回答必须尽量展示来源引用，来源字段可反查文档和片段。
- 安全性：API Key、数据库密码和模型密钥只能通过环境变量配置；密码不明文保存；用户资源需做权限隔离。
- 可用性：文档处理耗时较长时应展示处理状态；模型调用失败时应给出明确提示。
- 就绪性：存活探针只检查进程；就绪探针检查 MySQL 和 Chroma，不调用在线模型服务。
- 性能要求：普通业务查询应保持较短响应时间；实训规模下语义检索应在合理时间内返回候选片段。
- 可维护性：MySQL、Chroma、原始文件和外部模型服务职责清晰，后续可替换模型服务或优化检索策略。
- 一致性：API 字段命名、后端请求/响应模型和数据库字段应保持一致，避免历史记录模型出现多套并存。
- 兼容性：知识地图新增节点字段必须提供默认值，使旧历史 JSON 可以继续读取。
- 并发控制：知识地图分批分析和节点操作共享 LLM 并发限制，避免多个任务叠加压垮模型服务。
- 可恢复性：前端切换页面后可以恢复未完成的知识地图任务，并忽略旧任务迟到的轮询响应。
- 可观测性：后台处理失败原因应写入文档或任务记录，并能通过接口和日志定位。
- 会话安全：退出登录应通过持久化 Token 版本使既有 JWT 立即失效。
- 临时性：AI 练习提交、放弃或过期后必须清理，不建立长期试卷和答题记录。
