# 2026-07-22 混合检索升级说明

本文档用于将已有 CodeMind 环境升级到章节感知 Embedding、Dense + BM25 + RRF 混合召回和在线 reranker 版本。

## 变更影响

| 项目 | 是否需要迁移 | 说明 |
| --- | --- | --- |
| MySQL | 否 | 本次没有新增表、列、索引或约束，`database/schema.sql` 未变化，不需要执行 SQL migration。 |
| Chroma | 建议重建已有文档 | 新向量输入包含文件名、章节标题和正文，metadata 新增 `section_title`。旧向量仍可读取，但不会获得完整的章节感知效果。 |
| 后端配置 | 是 | 新增混合召回与 reranker 配置；`RERANK_API_KEY` 和 `RERANK_BASE_URL` 留空时复用系统 `LLM_*`。 |
| API 与前端 | 是 | 启用 rerank 时，`score_threshold` 和来源 `score` 表示证据相关度，默认值为 `0.55`；降级链路才使用 `0.45` 向量相似度。 |

章节标题只保存在 Chroma metadata，不写入 MySQL `document_chunks`，因此没有为本次升级创建空的 SQL 文件。后续若把章节标题变成结构化业务字段，再单独增加数据库列和迁移脚本。

## 配置变更

在 `backend/.env` 增加或确认以下配置：

```dotenv
RETRIEVAL_HYBRID_ENABLED=true
RETRIEVAL_DENSE_CANDIDATE_K=12
RETRIEVAL_LEXICAL_CANDIDATE_K=12
RETRIEVAL_FUSION_CANDIDATE_K=20
RETRIEVAL_LEXICAL_MAX_CHUNKS=3000
RETRIEVAL_RRF_K=60

# 留空时复用 LLM_API_KEY 和 LLM_BASE_URL
RERANK_API_KEY=
RERANK_BASE_URL=
RERANK_MODEL=Qwen/Qwen3-Reranker-8B
RERANK_TIMEOUT_SECONDS=30
RERANK_MAX_RETRIES=1
RERANK_SCORE_THRESHOLD=0.55
RERANK_FAIL_OPEN=true

# 只在 reranker 故障降级时使用
RETRIEVAL_SCORE_THRESHOLD=0.45
```

当前配置已经使用硅基流动的 LLM API Key 时，可以让 `RERANK_API_KEY` 保持为空。若 LLM 与 reranker 使用不同供应商或账号，则单独填写 reranker 的 API 根地址和密钥。Base URL 必须是 API 根地址，例如 `https://api.siliconflow.cn/v1`，不要填写 `/rerank`。

## Docker/VPS 升级步骤

升级不会删除 MySQL、上传文件或 Chroma 命名卷。生产操作前仍建议先备份：

```bash
cd /opt/codemind
git pull

cp backend/.env backend/.env.backup-20260722
docker compose exec -T mysql sh -c \
  'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' \
  > codemind-before-rag-upgrade-20260722.sql
```

更新 `backend/.env` 后重建服务：

```bash
docker compose up -d --build backend frontend
docker compose ps
curl -fsS http://127.0.0.1:8000/api/health/ready
docker compose logs --tail=100 backend
```

健康检查应返回 MySQL 和 Chroma 均为 `ok`。日志中若出现 `Reranker unavailable; using vector fallback`，说明服务正在使用降级链路，应检查模型名、API Key、Base URL、额度和网络。

## 已有文档索引升级

新上传文档会自动使用章节感知 Embedding。已有 `completed` 文档仍可检索，但旧向量没有章节标题 metadata。部署后在“文档库”中对已有文档逐个执行“重建索引”：

1. 确认文档当前状态为 `completed`。
2. 点击“重建索引”，等待状态重新变为 `completed`。
3. 重建任务成功后才会原子替换旧 MySQL 片段和 Chroma 向量。
4. 解析、Embedding 或 Chroma 写入失败时旧索引继续可用，不需要删除数据卷。

本次默认仍使用 `Qwen/Qwen3-VL-Embedding-8B` 4096 维，不要求一次性清空 Chroma。若同时更换了 Embedding 模型或维度，则不同维度向量不能混用，必须备份后完成全部文档重建。

## 验证建议

至少验证以下场景：

1. 上传带多级标题的 Markdown 或 DOCX，确认处理成功。
2. 使用正文事实提问，确认返回来源且分数不低于 `0.55`。
3. 使用只出现在章节标题中的关键词检索，确认可以命中对应片段。
4. 提问资料中不存在的精确数值、版本或配置，确认返回依据不足而不是主题相近片段。
5. 检查私人知识库不会召回其他用户资料，公共库可召回不同上传者的公共资料。

固定回归命令：

```bash
cd backend
python scripts/evaluate_quality.py validate
python scripts/evaluate_quality.py rag-hybrid \
  --output ../quality-results/rag-hybrid.json \
  --with-generation \
  --generation-positive-per-document 1
```

第二条命令会调用在线 Embedding、reranker 和 LLM，并消耗 API 额度。

## 回滚

本次没有 SQL migration，因此数据库不需要反向迁移。回滚时切回旧代码和镜像、恢复原 `backend/.env`，再重建后端与前端即可。旧版本会忽略 Chroma 中额外的 `section_title` metadata。

若升级期间同时更换了 Embedding 模型或维度，代码回滚前还应恢复对应的 Chroma 备份或使用旧模型重新建立全部向量，不能让不同模型或维度的索引混用。
